# Compatibility and semantic differences

Supported requests cover CRUD, mappings, bulk ingestion, common index lifecycle calls, multi-search, cursor pagination, basic lexical search, payload filters, source projection, count, indexed keyword terms facets, health, and durable aliases. A standalone `PUT /<index>/_doc/<id>` checks the authoritative document store so a new document returns HTTP 201 with `result: "created"`, while replacing an existing document returns HTTP 200 with `result: "updated"`. Contiguous bulk `index` actions remain optimized as one Qdrant upsert batch and currently report HTTP 201 per successful item without a created-versus-updated preflight. Standalone and bulk `create` operations first check for an existing document and return a 409 conflict rather than overwriting it; they are serialized within one gateway process but are not an atomic cross-replica compare-and-insert. The compatibility analyzer at `GET /_qdrant_gateway/compatibility` is local-only and reports request counts; no telemetry leaves the process.

Aliases currently map one alias to one concrete index. CRUD, search, count, mapping, and multi-search requests resolve that concrete index before selecting a Qdrant collection or deriving a deterministic point ID. Alias inspection is Elasticsearch-shaped and keyed by the concrete index. Multi-index aliases, filtered aliases, write-index selection, and native atomic alias switching remain unsupported.

Qdrant's server-side BM25 uses sparse vectors and its own tokenization/model implementation. Results should be evaluated by relevant document IDs and product metrics, not numerical `_score` equality with Elasticsearch. `match_phrase` currently uses the same native lexical representation and is therefore not a Lucene positional phrase guarantee.

Filter-only `should` clauses and numeric or percentage `minimum_should_match` are supported when they can be represented as Qdrant filter alternatives. `dis_max`, `match_bool_prefix`, and fuzzy-shaped requests are accepted through the gateway's lexical field path; their ranking and typo/prefix semantics are intentionally approximate because Qdrant's sparse model is not Lucene. Cursor pagination accepts `search_after` alongside explicit sort fields and returns the corresponding `sort` values in each hit; the cursor is stable only while the ordered result set is unchanged. Scripts, scroll, and analyzer settings that would materially change semantics remain unsupported. Every rejection identifies the request feature and a safe alternative where one exists.
# Pattern queries

`regexp`, `prefix`, and `wildcard` clauses are evaluated by the gateway using Rust's regular-expression engine after candidate documents are read from Qdrant. Positive pattern clauses can be combined with ordinary Qdrant-translated filters in `bool.must` or `bool.filter`; pattern clauses in `should` and `must_not` are rejected rather than approximated. A pattern-only query scans the collection in bounded scroll pages, so it is useful for modest catalog and identifier searches but should not be used as a substitute for a dedicated indexed pattern field at very large scale. Wildcards use Elasticsearch-style `*` and `?`; regular expressions use Rust/RE2-style syntax and reject invalid expressions with a structured 400 response.

Search responses also accept `post_filter` for simple term, terms, range, exists, and bool clauses. It is applied to hydrated hits after the main query, preserving the distinction between hit filtering and aggregation filtering for bounded result sets. Supported aggregation shapes now include terms, min, max, keyed filters, and simple filter wrappers; metric and filter counts are computed over the retrieved candidate set and should be treated as bounded until exact matching-document scans are enabled.
